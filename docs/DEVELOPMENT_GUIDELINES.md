## 一、项目目标与开发原则

本项目旨在开发面向医疗众筹申请者的 AI Agent，帮助用户整理病情叙述、解析医疗材料、检查材料完整性与信息一致性、补充缺失信息，并生成客观、可核查的申请初稿。

项目采用 **GitHub开源技术复用 + Agent工作流 + 前后端分离 + 独立事实校验** 的开发方式。

所有成员必须遵循：

1. **优先保证功能闭环。** 不追求复杂架构、过多功能或无必要的技术创新。
2. **优先复用成熟技术。** 不从零开发已有成熟解决方案，不在竞赛期间训练大型模型。
3. **严格限制开发范围。** 未经团队确认，不得擅自增加功能、引入新框架或重构其他成员代码。
4. **确保数据真实性。** AI不得编造病情、费用、诊疗经历、证明材料及来源引用。
5. **模块独立开发。** 每名技术成员对自己负责的模块具有完整开发及质量责任。
6. **统一接口规范。** 所有模块必须遵守 `contracts/` 内正式确认的接口契约。
7. **按期完成交付。** 10月22日晚冻结功能，10月23日完成内部验收，10月24日完成作品提交准备。

本项目不是医疗诊断系统，不提供医疗建议，不生成虚假证明，也不自动向真实众筹平台提交申请。

## 二、成员职责与交付要求

四名技术成员任务等级相同，原则上各投入约16–18小时，分别负责独立核心模块。

| 成员 | 负责模块 | 核心交付 |
|---|---|---|
| A | `agent/` | Dify工作流、信息抽取、智能追问、可信草稿生成 |
| B | `backend/` | FastAPI、OCR、文件处理、接口实现、系统集成 |
| C | `frontend/` | React用户端、表单、材料上传、结果展示、草稿编辑 |
| D | `validation/` | 证据追踪、材料完整性检查、事实冲突识别、最终校验 |
| E | 项目统筹 | 进度协调、测试组织、GitHub Issues、文档、演示与提交 |

**共同要求：**

- 每名技术成员必须提交可运行的功能代码、必要测试及模块使用说明。
- 不允许只提交页面截图、Prompt文本或未经运行验证的AI生成代码。
- 每人负责修复自己模块中的问题，不将本模块Bug转交其他成员。
- B负责系统集成和接口适配，但不额外承担其他模块的开发任务。
- E负责协调与验收，不承担四名技术成员的核心开发工作。
- 发现任务负担明显失衡时，由E协调调整，而不是默认由技术能力更强的成员加班完成。

## 三、项目目录与文件管理

统一使用以下目录：

```text
CareFund-AI/
├── frontend/        # C
├── backend/         # B
├── agent/           # A
├── validation/      # D
├── contracts/       # 公共接口契约
├── demo_data/       # 经批准的合成演示数据
├── docs/            # E
└── README.md
```

**文件管理要求：**

1. 原则上只修改本人负责的目录。
2. `contracts/` 为共享契约目录，任何修改必须经相关成员确认。
3. 不得随意修改其他成员的源码、配置或依赖文件。
4. 跨模块代码变更必须提前说明并经对应模块负责人同意。
5. 禁止提交 `.env`、API Key、Token、数据库密码及其他敏感凭据。
6. 禁止将真实患者的未授权资料、导师未经批准的数据上传GitHub。
7. 不允许提交虚拟环境、依赖缓存、构建产物及大规模原始数据。
8. 使用 `.gitignore` 排除不应提交的文件，不得直接删除其他成员已经提交的必要文件。

## 四、GitHub协作规范

### 4.1 分支分配

| 成员 | 固定工作分支 |
|---|---|
| A | `feature/agent` |
| B | `feature/backend` |
| C | `feature/frontend` |
| D | `feature/validation` |
| E | `docs/project` |

`main` 是项目稳定主分支。

**严禁直接向 `main` 提交未经审查的代码。**

所有成员在自己的分支上开发，完成后通过 Pull Request（PR）合并。

### 4.2 每日开发操作

开始开发前：

1. 确认当前位于自己的工作分支。
2. 检查工作区是否存在未提交的修改。
3. 获取最新远程信息，并根据团队约定同步 `main`。
4. 确认依赖、接口契约没有发生变更。

常用指令：

```bash
git status
git branch --show-current
git fetch origin
```

提交代码：

```bash
git add <本次修改的文件>
git commit -m "feat: describe your change"
git push origin <个人分支名>
```

其中 `<本次修改的文件>` 和 `<个人分支名>` 必须替换为实际路径与分支名称。

不得在不检查修改范围的情况下盲目使用 `git add .`。

### 4.3 Commit命名规范

统一采用：

- `feat:` 新增功能
- `fix:` 修复错误
- `refactor:` 重构代码
- `docs:` 修改文档
- `test:` 增加或修改测试
- `chore:` 工程配置或其他维护

例如：

```text
feat: implement medical document OCR
fix: correct evidence reference validation
docs: update agent workflow instructions
```

一次Commit尽量只完成一项明确任务，不得将大量无关修改混合提交。

### 4.4 Pull Request要求

每个PR必须说明：

- 本次实现了什么功能。
- 修改了哪些文件或模块。
- 是否涉及公共接口变化。
- 已完成哪些测试。
- 是否存在已知问题。

至少由一名非作者成员审查后再合并。涉及 `contracts/` 的修改必须取得受影响模块负责人的确认。

禁止使用 `git push --force` 覆盖共享分支，禁止在未确认影响范围时执行 `git reset --hard`、`git clean` 等破坏性命令。

出现Git冲突时及时沟通，不得直接覆盖他人修改。

## 五、统一接口与模块协作

**`contracts/` 是前端、后端、Agent与校验模块共同遵守的唯一接口契约来源。**

契约以经过测试和团队确认的版本为准；如果尚未通过测试，不得视为正式开发标准。

### 5.1 调用关系

```text
Frontend (C)
     |
     v
FastAPI Backend (B)
     |
     +---- Agent (A)
     |
     +---- Validation (D)
     |
     +---- OCR / 文件处理 (B)
```

具体规定：

1. C只调用B提供的API，不直接调用Dify或校验模块。
2. A按照约定的数据结构接收输入、返回候选事实、问题和草稿。
3. D接收标准事实及证据数据，返回规范化的校验结果。
4. B负责调用、转换、存储和整合各模块结果。
5. B负责维护申请状态和数据修订版本。
6. 四名开发者不得自行定义与正式契约冲突的同名字段、枚举和接口地址。

### 5.2 独立开发要求

为了避免相互等待：

- A使用模拟患者信息和材料解析结果开发Agent。
- B使用Mock Agent结果和Mock校验结果开发接口。
- C使用契约中规定的Mock JSON开发页面。
- D使用模拟事实、费用及证据数据开发校验程序。

**任何成员不得以其他模块尚未完成为由，推迟自己可独立开展的工作。**

### 5.3 接口变更流程

如需修改公共接口：

1. 提出具体修改理由。
2. 说明受影响的模块及字段。
3. 通知相关技术成员。
4. 先修改契约及对应示例、测试。
5. 契约变更通过审查后，再调整业务代码。

禁止口头约定一个新字段后直接在代码中使用。

字段新增、删除、类型变化、枚举变化、含义变化，都属于需要核对兼容性的接口变更。

## 七、医疗真实性与数据安全规范

这是本项目的强制性安全要求，所有技术模块均必须遵守。

### 7.1 AI事实约束

- 不允许生成用户未提供、材料未支持的具体病情、日期、医疗费用或诊疗经历。
- 不允许生成伪造诊断书、病历、发票及其他证明材料。
- 不允许为增强筹款效果而夸大疾病严重程度或经济困难。
- 对缺失信息只能提示补充、追问或留空，不得猜测填充。
- 对不同来源之间的矛盾，应标记待核实，不得擅自认定哪一方真实。
- AI不得自行创建虚假的证据ID、文件引用或页码。
- OCR识别结果仅代表从文件中提取的内容，不等于验证了材料真实性。
- 用户确认仅代表用户认可陈述，不等于平台审核通过。
- 只有经过必要规则校验的当前版本草稿，才允许进入最终确认和导出流程。

**不得仅依靠Prompt保证真实性。** 必须结合程序校验、证据引用检查、人工确认和状态约束。

### 7.2 数据安全

导师提供的数据首先由指定负责人确认使用授权、隐私处理要求和可使用范围。

未经授权，不得：

- 向公开GitHub仓库上传原始数据。
- 将可识别患者的病历、照片、视频或财务信息发送给第三方模型。
- 在演示视频、截图和提交材料中展示真实个人敏感信息。
- 将真实数据用于未经批准的训练、公开展示或分发。

优先使用合成案例开发和演示。

本次不进行大规模模型训练，不建设复杂医疗数据平台。

## 八、功能优先级与开发限制

### P0：必须完成

1. 用户基本信息填写及申请引导。
2. 图片/PDF医疗材料上传与文本解析。
3. 关键事实抽取及信息来源记录。
4. 材料缺失、事实冲突检查。
5. 针对缺失信息的智能追问。
6. 客观申请初稿生成、用户确认及导出基本申请包。

### P1：完成P0后优化

- 更清晰的核查结果展示。
- 草稿编辑体验。
- 错误提示及异常处理。
- 页面布局与交互细节。

### P2：本次原则上不开发

- 视频理解。
- 复杂语音交互。
- 多平台自动申请。
- 大规模模型训练或微调。
- 筹款成功率预测。
- 医疗诊断与治疗建议。
- 复杂多Agent自主协作。

任何新功能必须经过团队讨论，并确保不会影响P0完成时间。

## 十、测试与验收规范

每名成员在提交PR之前，必须完成自己模块的基本测试。

### 基础测试

- 正常输入是否可用。
- 缺失字段是否正确处理。
- 错误输入是否有合理提示。
- API是否符合正式契约。
- 空值、异常值是否引起崩溃。
- 模块是否可以独立运行。
- 是否存在敏感信息泄露风险。

### 必须验证的完整场景

**场景一：** 正常申请，能够完成材料解析、事实整理和初稿生成。

**场景二：** 缺失部分医疗信息，系统能够正确提示补充。

**场景三：** 自述与证明材料存在金额或日期冲突，系统能够发现并提示。

**场景四：** 用户要求AI夸大病情或虚构费用，系统不能输出编造的申请事实。

**场景五：** 用户修改已确认信息后，相关旧分析或旧草稿必须失效，防止错误导出。

所有发现的问题记录至GitHub Issues，标明严重程度、复现步骤、负责人及处理状态。

不得仅凭页面显示正常就认定功能通过测试。

## 十三、团队共同遵守的五条底线

**1. 不编造：** 不允许AI虚构任何医疗事实、费用或证明材料。

**2. 不越权：** 不随意修改其他成员模块、公共接口及稳定主分支。

**3. 不失控：** 不擅自增加功能或引入影响进度的复杂技术。

**4. 不虚报：** 不将未经验证的功能、测试数据或模型效果作为已完成成果。

**5. 不延期：** 所有开发以10月22日功能冻结、10月23日内部验收、10月25日正式截止为约束。

**本项目的最终目标不是功能数量最多，而是在规定时间内交付一个完整、稳定、可信、具有清晰创新点的医疗众筹智能申请助手。**

所有成员应在正式开发前阅读并确认本规范；执行过程中如需调整，由团队共同协商，并同步更新正式文档。
